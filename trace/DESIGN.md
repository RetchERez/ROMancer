# v1.1: reach every ROM, and show every change

## Goal

Palette and background editing for all 942 supported revisions, with no
per-game maps. Before anything is saved, the person editing sees every place
the change shows up.

## How ROMancer finds things: tracing engines

Each engine has a second build, the tracing build. It tags every byte of
palette RAM, video RAM and work RAM with the ROM byte its value came from
(`romancer_trace.h`). The pinned playtest engines are unchanged.

A tag is one of:

- **ROM data**: copied from a data byte, directly or by DMA.
- **Code value**: an immediate operand, such as a Game Boy `ld a,$E4` before
  `ldh [$47],a` or a Mega Drive `move.w #$0EEE`.
- **Derived**: computed from ROM data. Examples are fades, decompressed
  tiles, and run-length output.

Tags are claims. ROMancer calls an edit *verified* only after the causal
check (`trace_probe.py --causal`) has passed: change the ROM byte, replay
from the same state, and confirm that the screen byte changed.

## Scenes: where things appear

A scene is a savestate plus its trace: which ROM bytes feed the visible
palettes, tiles and maps at that moment. ROMancer collects scenes:

1. automatically, from the catalog boot routes (title screen and first
   gameplay for every revision), and
2. from ordinary play. Whenever you pause Playtest, that moment becomes a
   scene. Playing through a battle teaches ROMancer about that battle.

Inverting the scenes gives the impact index: for any ROM byte, the list of
scenes that use it.

## What the editor shows

**Click to edit.** Pause Playtest and click anything on screen: a color, a
background, a sprite. ROMancer opens the bytes behind it, already in the
right format (palette entries, tiles, tilemap).

**"Also changes" strip.** Next to the editor is a thumbnail of every known
scene that uses the same bytes. Each thumbnail is re-rendered by the real
engine from its savestate with the edit applied, not predicted. Scenes that
end up looking different from the one being edited are flagged first.

**Shared data, stated plainly.** For example: "This battle background is
shared by 14 battle areas. Change all 14, or only this one?" Choosing
"only this one" copies the data to free ROM space and repoints that single
use. The pointer location is known because the tracer also tags the bytes
that formed the DMA or decompressor source address.

**Coverage, stated plainly.** For example: "Seen in 14 scenes. Places you
haven't played yet can't be shown." It also notes when other code reads the
same bytes but was never seen drawing them.

**Change list before saving.** A plain-language list of every edit, the
scenes it affects with before/after thumbnails, the byte count, and the
checksum update. Each edit can be turned off, and Save writes a separate
playable build. This replaces the byte-level "Technical details" as the
main review. The bytes stay one click away.

## Per-ROM coverage report

For every revision, the report shows the following, so "every ROM" is
measured rather than assumed:

- palette sources found, and the share that passed the causal check;
- tile sources found: plain, compressed with a known codec, compressed with
  an unknown codec, or generated by code;
- the editing path that applies: direct, re-encode, or relocate and
  repoint.

## Colors the tags do not lead to: looking in the ROM

A tag names the last ROM byte that went into a value. For most palettes that
is the color itself. It is not when the game fades the palette through work
RAM (every color is then *computed*, even at full brightness), when a
cartridge coprocessor prepares the palette (SA-1, SuperFX: the hooks follow
the main CPU only, so the colors arrive with no tag at all), or when the
palette is put together from table bytes. The stored color is usually still
in the ROM, and `romancer/palette_trace.py` looks for it in four ways, each a
proposal that only a replay turns into an edit:

- **Another scene.** A scene recorded a moment earlier or later often traced
  the same entry, holding the same color, straight to the ROM.
- **A plain copy of the palette line** (`stored_copies`). The longest stretch
  of neighbouring entries, this one included, that the ROM holds byte for
  byte. One repeated value is never accepted, and a copy next to the entry's
  traced offsets comes first.
- **A number in the program** (`constant_places`), for one-byte palettes: a
  load-a-number instruction holding the value, with a neighbour of the same
  palette set close by.
- **Measurement** (`plan_by_measurement`). When single bytes are known to move
  the entry but none is the color, every bit of those bytes and their
  neighbours is flipped on its own and replayed. If the effects combine, the
  flips that give the wanted color are written together and replayed once
  more. A Game Boy shade register built two bits at a time from a fade table
  is edited this way.

The editor offers this as "let ROMancer look for it" on a locked color
(`scene_graphics._plan_color`), and keeps the result only when the replay
shows exactly the picked color in that entry and no other palette entry
moved, except entries that held the same color and follow it. The coverage
sweep runs the same searches, and also looks at a scene every 300 frames and
plays a second input script before it gives up on a ROM, because a title
screen that fades in and out can be blank at every coarser sample.

## Tiles the game computes: the overlay

Some tiles are not stored anywhere in a form ROMancer can rewrite: the game
unpacks them with a codec ROMancer does not know, or builds them in code.
For those there is a fallback that does not depend on how the game makes
the tile. A small routine is added to the vertical-blank interrupt. Each
frame it looks at the tile's slot in video memory; when the slot holds
exactly the original tile, it writes the edited one. Anything else in the
slot is left alone. `graphics_trace.plan_overlay_patch` builds it for every
processor (`OVERLAY_STATUS`).

Where the routine goes, per system: free ROM in memory that is always
mapped; or free ROM in another bank behind a short stub that pages it in
and puts the game's bank back; or ROM added at the end. Nothing is
overwritten that is not a run of padding.

The video chips' address registers cannot be read back, so the routine
cannot restore what it found. It therefore stays out of frames in which the
game may have a transfer of its own under way (it works only while the
interrupted program is waiting, where that can be told), and the planner
tries the careful variants first.

## Background cells the game builds: the stored piece

A background cell holds a tile number. Where that number is a ROM byte it
is written in place, and where the map is packed with a known codec it is
unpacked, changed and packed again. Many games do neither: they build the
screen from blocks of cells (a level is a grid of block numbers, and a
table holds the cells of each block), or read the number from a table and
add a base to it. Such a cell is tagged *derived*, and the tag names the
last ROM byte the game read before writing it, which is usually the
piece itself.

`cell_trace.plan_cell_edit` therefore tries the ROM bytes at and around
that traced byte, one at a time: the byte is moved by as much as the cell
has to move, the scene is replayed, and the place counts only when the cell
then holds exactly the planned value. Two things are refused even then: a
place that also changes video memory outside the background maps, and a
byte the game adds to every cell it draws (a quarter of the layer moves
with it). And because the place is found by trying, not traced, it must
hold over the longest replay there is: the recording replayed from its
first savestate (power-on, when it began there) must end with the cell as
planned and nothing outside the maps changed. A byte that gives the cell
from a moment before the scene, but sends the game another way when it is
played from the start, is not a piece of the background.

Changing a stored piece changes every place the game draws with it. The
plan lists the other cells of the scene that changed (`also_cells`), the
editor says how many before the change is kept, and the "Also changes"
strip re-renders every recorded scene whose trace names the changed bytes.

Which picture a cell shows is its tile number. The cell's other stored byte
(the NES attribute byte of a 4x4 block, or the upper byte with a palette or
priority bit on the 16-bit systems) is often computed even when the tile
number is a plain ROM byte. A change is planned byte by byte: painting a
picture needs only the tile number, so such a cell is written in place, and
the sweep picks its cells by the tile number (`cell_trace.tile_status`).

## What counts as confirmed

Three facts are recorded for an edit, and they are kept apart:

- **As planned in the scene.** The scene is replayed from a checkpoint
  shortly before it with the edited ROM; the planned bytes hold their
  planned values. This is the test every editing path must pass
  (`verify_plan`).
- **Clean from power-on.** The whole recorded run is repeated with the
  edited ROM and reaches the scene changed only as planned
  (`verify_from_power_on`).
- **Why not, when it is not clean.** Added code makes a game run a few
  cycles later, and some games then take a different course on their own.
  So the same run is repeated with the bare interrupt hook, and with a
  routine of the same cost that touches nothing in the video chip. If
  those runs differ too, the original run is no reference for this game and
  nothing is laid at the overlay's door. If they reproduce the original run
  and the overlay does not, the overlay's video access disturbs the game
  (`overlay_safety`).

`trace/graphics_sweep.py` measures all three for every ROM in the corpus.
