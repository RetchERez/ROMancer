# v1.1: reach every ROM, and show every change

## Goal

Palette and background editing for all 1,052 supported revisions, with no
per-game maps. Before anything is saved, the person editing sees every place
the change shows up.

## How ROMancer finds things: tracing engines

Each engine has a second build, the tracing build. It tags every byte of
palette RAM, video RAM and work RAM with the ROM byte its value came from
(`romancer_trace.h`). The pinned playtest engines are unchanged.

A tag is one of:

- **ROM data**: copied from a data byte, directly or by DMA.
- **Code value**: an immediate operand, such as a Game Boy `ld a,$E4` before
  `ldh [$47],a` or a Mega Drive `move.w #$0EEE`.
- **Derived**: computed from ROM data. Examples are fades, decompressed
  tiles, and run-length output.

Tags are claims. ROMancer calls an edit *verified* only after the causal
check (`trace_probe.py --causal`) has passed: change the ROM byte, replay
from the same state, and confirm that the screen byte changed.

## Scenes: where things appear

A scene is a savestate plus its trace: which ROM bytes feed the visible
palettes, tiles and maps at that moment. ROMancer collects scenes:

1. automatically, from the catalog boot routes (title screen and first
   gameplay for every revision), and
2. from ordinary play. Whenever you pause Playtest, that moment becomes a
   scene. Playing through a battle teaches ROMancer about that battle.

Inverting the scenes gives the impact index: for any ROM byte, the list of
scenes that use it.

## What the editor shows

**Click to edit.** Pause Playtest and click anything on screen: a color, a
background, a sprite. ROMancer opens the bytes behind it, already in the
right format (palette entries, tiles, tilemap).

**"Also changes" strip.** Next to the editor is a thumbnail of every known
scene that uses the same bytes. Each thumbnail is re-rendered by the real
engine from its savestate with the edit applied, not predicted. Scenes that
end up looking different from the one being edited are flagged first.

**Shared data, stated plainly.** For example: "This battle background is
shared by 14 battle areas. Change all 14, or only this one?" Choosing
"only this one" copies the data to free ROM space and repoints that single
use. The pointer location is known because the tracer also tags the bytes
that formed the DMA or decompressor source address.

**Coverage, stated plainly.** For example: "Seen in 14 scenes. Places you
haven't played yet can't be shown." It also notes when other code reads the
same bytes but was never seen drawing them.

**Change list before saving.** A plain-language list of every edit, the
scenes it affects with before/after thumbnails, the byte count, and the
checksum update. Each edit can be turned off, and Save writes a separate
playable build. This replaces the byte-level "Technical details" as the
main review. The bytes stay one click away.

## Per-ROM coverage report

For every revision, the report shows the following, so "every ROM" is
measured rather than assumed:

- palette sources found, and the share that passed the causal check;
- tile sources found: plain, compressed with a known codec, compressed with
  an unknown codec, or generated by code;
- the editing path that applies: direct, re-encode, or relocate and
  repoint.
